1. Executive Summary

The ChainGuard frontend is a dashboard-style investigation console designed for blockchain forensic analysis, wallet investigation, fraud detection review, graph exploration, and AI-assisted investigation. The project is built using React and TypeScript with Vite as the build tool. The application is organized as a single-page frontend with a persistent sidebar, top status bar, and dynamically rendered content panels for investigation actions.

The current implementation follows a state-driven UI model rather than a React Router route system. The root application component holds the current screen state, and the visible content changes depending on the current navigation state. The frontend exposes a dedicated API layer under src/api.ts to integrate with backend services for case data, transaction details, risk assessments, paths, attribution, and AI interpretation endpoints.

The project structure is intentionally modular and easy to extend. It separates the layout shell, reusable visual primitives, screen components, and API integration layer. This makes it suitable for a backend team to integrate real endpoints without a complete frontend rewrite.

2. Frontend Purpose and Responsibilities

The frontend is responsible for:

  • Rendering the investigation dashboard shell and navigation.
  • Displaying case metadata such as wallet IDs, risk status, and investigation context.
  • Rendering investigation screens: overview, new case, transactions, risk, attribution, AI interpretation, timeline, graph, and report.
  • Managing UI state for screen selection, tab navigation, and side-panel visibility.
  • Calling backend API endpoints through a dedicated service abstraction.
  • Handling loading and error states for data fetching.
  • Preparing the UI for real backend data without hard-wired business logic.

The frontend is not a complete backend implementation; it is a presentation and orchestration layer that expects the backend to provide real investigation data through the API contract defined in src/api.ts.

The frontend is structured around a root app shell that owns the primary navigation state and orchestrates screen rendering. It is not nested route-based. Instead, it uses the current screen value stored in React state to decide which component to render.

Application responsibilities are intentionally split into layers:

  • Shell layer: layout, sidebar, top bar
  • Component layer: reusable controls and visual building blocks
  • Screen layer: overview, investigation workspace, new investigation, transactions, attribution, etc.

6. Application Entry Point and Startup Flow

The startup flow is simple and follows the standard Vite/React pattern.

  1. src/main.tsx creates the root React application.
  2. It wraps the app in ReactFlowProvider from reactflow so graph features can render correctly.
  3. App is mounted and rendered by React.
  4. App initializes states such as current screen, transactions, graph data, risk data, and WebSocket status.
  5. A useEffect hook triggers data loading on initial mount in App.tsx.
  6. Backend data is fetched through the service layer defined in src/api.ts.
  7. Content is rendered according to the current screen state.
Entry point: src/main.tsx
App bootstrap: ReactDOM.createRoot(...).render(<App />)

9. Component Architecture

The project uses a clear component hierarchy around a reusable design system.

  • Layout shell: sidebar, top bar, and main region.
  • Reusable components: buttons, cards, badges, metric cards, risk display, drawers, evidence cards, AI panel.
  • Screen-level components: Overview, NewInvestigation, Transactions, RiskAndFraud, Attribution, AIInvestigation, Timeline, FundFlow, InvestigationGraph, InvestigationReport.
  • Workspace component: sets the active sub-tab and renders the correct screen content for the investigation workspace.

Reusable UI primitives are located in src/components/BaseComponents.tsx and are imported by the screen components.

11. Data Flow

The application follows the following flow:

User → UI interaction → React state update → component render → API/service call → backend response → state update → component re-render
  • User clicks navigation item or tab.
  • Current state is updated through React hook setters.
  • Component rendering changes based on this state.
  • When data is needed, App.tsx calls the methods in src/api.ts.
  • The service layer uses fetch and constructs endpoint URLs from the configured base URL.
  • Server responses are mapped into typed structures such as Transaction, Graph, RiskAssessment, and Attribution.
  • UI screens display these values through screen components and base components.

The frontend currently has a dedicated service layer in src/api.ts. This is the main backend integration contract for the UI.

WebSocket realtimeUrl(caseId) Live updates for new transactions/events

Environment variables used in the project are:

VITE_API_BASE
VITE_WS_BASE
VITE_CASE_ID
VITE_WALLET_ADDRESS

These variables are read from the environment and used to configure the backend API base URL and WebSocket URL generation. The app also uses a fallback default of /api for REST calls.

Authentication integration points are not implemented in the current project source. There is no token or auth interceptor in the frontend service layer. Any future auth implementation would need to be introduced in the same API layer without restructuring the screens.

CORS readiness depends on backend configuration. The frontend performs browser fetches to the configured API base and generates WebSocket URLs. The backend must allow the frontend origin for cross-origin requests if the app is served from a different domain or port.

13. Demo, Mock and Placeholder Data

There is no embedded demo dataset in the current primary app state flow. The project is intended to pull real backend data through the service layer.

However, some UI states still include generic placeholders or fallback wording, such as:

  • "AI analysis not yet available. Processing investigation data..." in AIInvestigation
  • "This section is under development." in the default workspace switch case
  • Empty-ui fallbacks such as "No Active Investigation" displayed when no case data is present

These are not backend mock models; they are UI fallbacks for empty or unavailable data. The primary data source is expected to be the real backend API service layer.

14. Error Handling

The project includes basic frontend error handling patterns:

  • API errors are caught in App.tsx and stored in a local error state.
  • Loading state prevents repeated actions during fetches.
  • WebSocket failures set the realtime status to disconnected.
  • Network data failures are handled gracefully and leave the UI in a neutral/loading-ready state.

Relevant warnings and runtime issues previously encountered in this project were tied to missing imports, stale app navigation state, and missing app-level sync between sidebar state and workspace content. Those issues were addressed in the app logic by restoring the required React imports and aligning the state-driven navigation flow.

There is no global error boundary in the current application; this is a future improvement if the project grows beyond the current dashboard scope.

17. Backend Integration and Git Merge Readiness

The frontend is already organized to accept a separately developed backend with minimal disruption.

  • All API calls are centralized in src/api.ts.
  • UI screens consume typed model objects instead of inlined data fetch logic.
  • Data objects are modeled explicitly in TypeScript interfaces.
  • Environment variables isolate backend host and WS configuration.
  • There is no backend logic embedded in screen components.

This means a backend team can connect the actual endpoints with minimal frontend code changes, as long as the response shapes match the existing TypeScript definitions.

It is important not to restructure the frontend unnecessarily; the app currently demonstrates a straightforward separation of concerns and is suitable for a merge-oriented workflow.

18. Deployment Readiness

The frontend is deployable as a standard Vite static client application.

  • Build output is generated under the dist folder.
  • Environment variables should be configured during deployment.
  • API host and WebSocket base must be set according to the target backend environment.
  • The app is ready for deployment to a web server that can serve the built static assets and route requests to the backend API.

It is not a server-side rendered application and does not require a database or backend runtime on the frontend itself.

19. Developer Handover Guide

For another developer joining the project:

  1. Start with src/App.tsx to understand the navigation and app-state flow.
  2. Review src/api.ts to see backend contracts and environment variables.
  3. Read src/components/Layout.tsx for the main navigation shell.
  4. Review src/components/InvestigationWorkspace.tsx for workspace tabs and investigation rendering logic.
  5. Check screen components in src/screens to see what each page is expected to display.
  6. Use src/styles/theme.css for design tokens and visual consistency.
  7. When integrating backend data, keep the service layer as the single integration boundary.

20. Backend Integration Checklist

  • Define backend endpoints for transactions, graph, paths, risk, attribution, and AI summary.
  • Confirm response shapes match the TypeScript models in src/api.ts.
  • Set the environment variables for the API base and websocket address.
  • Ensure CORS is configured for the frontend origin.
  • Integrate a real case id and wallet address source.
  • Update UI states for loading and empty data where needed.
  • Verify real-time event payload compatibility with the existing WebSocket handling code.
  • Keep any future auth implementation inside the API service layer.
